# ADR-0014 — Cilium version selection for Linux kernel 7.2+

- **Status:** Accepted — **superseded in part by [ADR-0015](ADR-0015.md)**
  (the post-install `cilium upgrade` steps were removed in favour of one
  `cilium install` carrying all values)
- **Date:** 2026-09-13

## Context

Cilium's agent cannot start on Linux kernel 7.2+: kernel commit `b1f7f67b74c2e`
("bpf: Add validation for `bpf_set_retval` argument") makes the verifier reject
Cilium's generic helper probe, which emits a bare `call bpf_set_retval` at
program entry where `R1` is the program-context pointer. Cilium's
`HaveProgramHelper` treats any non-`ErrNotSupported` verifier error as fatal,
so the agent crash-loops:

```
level=fatal msg="failed to probe helper" ... detect support for FnSetRetval for
program type CGroupSock: load program: invalid argument: 0: (85) call
bpf_set_retval#187: R1 is not a scalar
```

and `cilium install --wait` times out (`DaemonSet/kube-system/cilium not
ready ... Available: 0/1`). Upstream issue cilium#48016 was fixed by commit
`67c619cb0a43c7178bf843c9281fc77fe64fe13f` ("bpf: use
`bpf_core_enum_value_exists()` for HAVE_SET_RETVAL") and backported as
cilium#48376 (v1.19) / cilium#48381 (v1.18), but **no stable release contains
the fix as of 2026-09-13** — v1.18.13/v1.19.7/v1.20.1 were all published
2026-08-18. The first release with it is **v1.21.0-pre.2** (2026-09-09),
proven live end-to-end on kernel 7.2.4.

Getting the agent to start exposed two latent cilium-cli defects: post-install
`cilium install --set ...` fails with `release name check failed: cannot reuse
a name that is still in use`, and `cilium clustermesh enable` fails on kind
with `cannot auto-detect service type, please specify using '--service-type'
option`.

## Decision

- **Kernel-aware version policy** — `provision::cilium_version_for_kernel(kernel)`
  is pure policy: `(major, minor) >= (7, 2)` returns
  `manifests::CILIUM_VERSION_KERNEL_72 = "v1.21.0-pre.2"`; anything else
  returns `None` (let the cilium CLI pick its default stable release). The
  constant is the single bump point once a stable release contains the fix.
- **Probe the kernel the nodes run on** — `provision::detect_cilium_version()`
  runs `docker info --format '{{.KernelVersion}}'` (the kernel kind nodes —
  and therefore the Cilium agent — run on; on macOS that is the Docker Desktop
  VM kernel). If docker cannot be reached or the probe fails, fall back to the
  CLI default stable; the failure diagnosis below still catches the crash-loop.
- **Version on every Cilium step** — `build_plan_with_cilium_version(spec,
  data_dir, kubeconfig, cilium_version)` threads the resolved version into
  every `cilium install`/`cilium upgrade` step. A later step without
  `--version` would silently downgrade to the broken stable and re-break the
  agent. The app worker resolves the version once per cilium cluster and calls
  this entry point; `build_plan` remains the `None` (CLI default) wrapper.
- **`cilium upgrade` for post-install values** — the base install stays
  `cilium install`; the ingress and Gateway API `--set` steps use
  `cilium upgrade`, which preserves previously set values and accumulates new
  ones. *(Superseded by ADR-0015: all values now go into the single
  `cilium install`.)*
- **Clustermesh service type** — `cilium clustermesh enable --service-type
  NodePort`, matching the Helm value `clustermesh.apiserver.service.type=NodePort`
  the plan already sets (kind has no LoadBalancer for the CLI to detect).
- **Diagnosis stays as fallback** — the existing agent-log inspection
  (`failed to probe helper` + `FnSetRetval`/`bpf_set_retval`) remains, with its
  remedy text updated to the new truth: kindboard selects the fixed version on
  kernel >= 7.2; check `docker info --format '{{.KernelVersion}}'`, boot an
  older kernel, or use flannel/calico.

Alternatives considered (rejected):

- **Pin v1.21.0-pre.2 for everyone** — forces a pre-release onto hosts whose
  stable Cilium works fine. Rejected.
- **Boot an older kernel / wait for a stable release** — outside the app's
  control, and leaves Cilium unusable on kernel-7.2-only hosts indefinitely.
  Rejected as the primary fix (still a documented fallback).
- **Ship a patched Cilium image** — custom CNI logic; violates the "drive the
  official binaries" principle (ADR-0008). Rejected.

## Consequences

- kindboard depends on a Cilium pre-release (`v1.21.0-pre.2`) on kernel >= 7.2
  until a stable release contains the fix; bump `CILIUM_VERSION_KERNEL_72`
  (single constant) when it does.
- Kernel-probe failure degrades to the previous behavior: stable Cilium plus
  the existing crash-loop diagnosis.
- macOS is covered automatically — the probe reads the Docker Desktop VM
  kernel the kind nodes actually use, not the Darwin host version.
- Hosts on older kernels are unaffected: no `--version`, CLI default stable,
  exactly as before.
- Live verification (kernel 7.2.4, 2026-09-13): Cilium/Operator/Envoy OK,
  Hubble relay+UI Running, Gateway API enabled, ingress controller enabled,
  clustermesh-apiserver 3/3 Running, `cilium status` exit 0.

## Verification

- Unit tests for `cilium_version_for_kernel`: `(7, 2)` and newer → the fix
  version; older (6.x, 7.0/7.1) and malformed/empty input → `None`.
- Plan tests: every `CiliumInstall` step in a cilium plan carries the resolved
  version; clustermesh passes `--service-type NodePort`. (Superseded by
  ADR-0015: the post-install `CiliumUpgrade` value steps were removed — a
  single `cilium install` carries all values; see ADR-0015 §Verification.)
- Live e2e (kernel 7.2.4): CNI matrix green — flannel ✓, calico ✓, cilium ✓
  (full stack), `cilium status` exit 0.
