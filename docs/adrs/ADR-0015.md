# ADR-0015 — Cilium on kind: kube-proxy replacement and Gateway API CRDs

- **Status:** Accepted
- **Date:** 2026-09-13

## Context

Round 1 (ADR-0014) got the Cilium agent to start on Linux kernel 7.2, but the
Cilium extras still did not work: the Gateway API controller never reconciled
(`GatewayClass/cilium` stayed `Accepted=Unknown reason=Pending`) even after the
agent came up. Live investigation found three independent causes:

- **kube-proxy replacement gates the Gateway API controller.** Cilium's
  operator disables its Gateway API cell unless kube-proxy replacement is
  enabled — `operator/pkg/gateway-api/cell.go` logs *"Gateway API support
  requires kube-proxy-replacement enabled"* (present in v1.20.1 and v1.21).
  kindboard had been installing Cilium with `kubeProxyReplacement=false` on top
  of kind's active kube-proxy, so the controller was never started.
- **Cilium >= 1.21's operator requires newer Gateway API CRDs.** It watches
  `tlsroutes` v1 and `referencegrants` v1; the previously pinned Gateway API
  v1.4.0 standard-install ships those kinds only at v1alpha3/v1beta1. Gateway
  API **v1.6.2** standard-install ships both at v1 (verified: the release
  bundle's CRDs declare `versions: [v1]` for `tlsroutes` and
  `referencegrants`).
- **The operator discovers CRDs once at startup.** It reads
  `enable-gateway-api` and discovers the Gateway API CRDs when it boots; a
  later `cilium upgrade` updates the configmap but does not roll the operator
  pod (the upgrade even warns *"you maybe need to restart Cilium pods"*). The
  CRDs therefore have to be present *before* the install, not applied
  afterwards.

The post-install `cilium upgrade` steps also carried a latent failure mode:
running them against an existing release fails with `release name check
failed: cannot reuse a name that is still in use`.

All of the above was reproduced live and then verified fixed on kernel 7.2.4
with Cilium v1.21.0-pre.2 (the version selected by ADR-0014's kernel policy).

## Decision

- **Cilium clusters run without kube-proxy.** The rendered kind config sets
  `networking.kubeProxyMode: none`; Cilium is installed with
  `kubeProxyReplacement=true`, i.e. Cilium fully replaces kube-proxy (kind's
  kube-proxy would otherwise own service routing, and Cilium's Gateway API
  controller requires replacement).
- **Gateway API CRDs are pinned to v1.6.2 and applied before the install.**
  `manifests::GATEWAY_API_CRDS_URL` points at the v1.6.2 `standard-install.yaml`
  (SHA-256 `faede450fa178126aba41337737b97d351ebe87d93c910237ce1e072d1ca40d9`),
  downloaded and server-side applied as the first cilium step whenever the
  Gateway API extra is enabled.
- **One `cilium install` carries all values.** The install sets
  `kubeProxyReplacement=true`, the clustermesh pair (`cluster.name`/`cluster.id`
  plus `clustermesh.apiserver.service.type=NodePort` when mesh is on),
  `ingressController.enabled=true` (the default ingress) and
  `gatewayAPI.enabled=true` when selected. No post-install value upgrades.
- **The extras flow is:** (if Gateway API) CRDs download + apply → one
  `cilium install` with all values → `cilium hubble enable --relay --ui` →
  `cilium clustermesh enable --service-type NodePort` → final
  `cilium status --wait`. `KindCommand::CiliumUpgrade` and the post-install
  upgrade steps are removed.

Alternatives considered (rejected):

- **Keep `kubeProxyReplacement=false` and drop the Gateway API extra** — kind's
  kube-proxy keeps working and nothing else changes, but Cilium's Gateway API
  feature becomes permanently unavailable, since the controller cannot run
  without replacement. Rejected.
- **Per-extra mode switch** (enable replacement only when Gateway API is
  selected) — makes the rendered kind config depend on extras and leaves two
  provisioning shapes to test; Cilium's supported kind configuration is full
  replacement. Rejected.
- **Apply the CRDs post-install and force the operator to restart** — works
  around the once-at-startup discovery with an extra rollout-wait step and
  stays order-sensitive; applying the CRDs before the install matches Cilium's
  documented Gateway API install order and is simpler. Rejected.

## Consequences

- Cilium clusters have no kube-proxy: Cilium owns service routing (ClusterIP,
  NodePort, LoadBalancer, hostPort). This is the supported Cilium-on-kind
  configuration, but kube-proxy-specific behavior is gone by design.
- The Gateway API CRD pin is coupled to Cilium's required GVKs: bump
  `GATEWAY_API_CRDS_URL`/`GATEWAY_API_CRDS_SHA256` when Cilium requires a newer
  Gateway API bundle.
- **kind has no cloud LoadBalancer.** Cilium's Gateway API controller is fully
  functional (GatewayClass and HTTPRoutes reconcile), but a user-created
  `Gateway`'s service stays `EXTERNAL-IP: <pending>` until the user configures
  NodePort/hostNetwork or a `CiliumGatewayClassConfig` — a kind/host caveat,
  documented as such, not a kindboard provisioning failure.
- The `release name check failed: cannot reuse a name that is still in use`
  failure mode is gone: there are no post-install release upgrades.
- ADR-0014's kernel-aware version policy is unchanged — the single install
  carries the resolved `--version`.

## Verification

- Plan tests: a cilium plan contains exactly one `CiliumInstall`; it carries
  `kubeProxyReplacement=true`, the ingress/Gateway/mesh values and the resolved
  version; the Gateway API CRDs step precedes the install; no `CiliumUpgrade`
  steps remain; the rendered kind config sets `kubeProxyMode: none`.
- Live (kernel 7.2.4, Cilium v1.21.0-pre.2): a single install with all values
  starts the operator with `enable-gateway-api=true` and
  `kube-proxy-replacement=true`; `GatewayClass/cilium` is `Accepted=True`; a
  test `HTTPRoute` is `Accepted=True ResolvedRefs=True`; the per-Gateway
  `CiliumEnvoyConfig` and `cilium-gateway-*` service are created; DNS
  (`nslookup kubernetes.default`) resolves; `cilium status` is OK for
  Cilium/Operator/Envoy/Hubble/ClusterMesh.
