# ADR-0022 — Hover text: gray on a neutral fill, not `on_accent` on the accent

- **Status:** Accepted
- **Date:** 2026-09-15

## Context

kindboard's R8 widget styling (theme-contract.md §7) paired hovered widgets with the
accent fill and `on_accent` text:

```rust
visuals.widgets.hovered.bg_fill = pal.accent;
visuals.widgets.hovered.fg_stroke = Stroke::new(1.0, pal.on_accent); // WHITE on Light
```

User report: **"the mouse over letters can't be white — it should be gray, to be
seen on any theme"**. Hover letters were turning white (Light theme) and
disappearing.

### Root cause (verified against vendored egui 0.36.2 sources)

egui buttons and selectable labels do **not** paint their hover fill from
`widgets.hovered.bg_fill`. `Style::button_style` (`src/widget_style.rs`) builds the
button frame from **`weak_bg_fill`**:

```rust
ButtonStyle {
    frame: Frame {
        fill: visuals.weak_bg_fill,   // ← hovered.weak_bg_fill, never overridden
        ...
    },
    text_style: ws.text,              // ← ws.text.color = hovered.fg_stroke.color
}
```

kindboard set `hovered.bg_fill` (unused by buttons) and `hovered.fg_stroke`
(= `on_accent` = **white** in the Light palette), but left `hovered.weak_bg_fill`
at egui's default `gray(220)` (light) / `gray(70)` (dark). Result:

- **Light:** white letters on a light-gray hover fill — invisible.
- **Dark / HighContrast:** near-black letters on dark-gray — poor contrast.

The same gap existed for the pressed state (`active.weak_bg_fill` untouched).

## Decision

Hover becomes a **quiet neutral state with gray text**, chosen per theme and
locked by a contrast regression test (WCAG AA, ≥ 4.5:1, ITU-R BT.709):

| field | Dark | Light | HighContrast |
|---|---|---|---|
| `hover_fill` | `0x27323d` | `0xdce3ea` | `0x1a1a1a` |
| `hover_text` | `0xc6cfd9` | `0x37424d` | `0xd3d9de` |

Measured contrast: **dark 8.3:1 / light 7.9:1 / HC 12.2:1**.

`apply_theme` now writes both fills for both states:

```rust
visuals.widgets.hovered.weak_bg_fill = pal.hover_fill; // the one buttons paint
visuals.widgets.hovered.bg_fill      = pal.hover_fill;
visuals.widgets.hovered.bg_stroke    = Stroke::new(1.0, pal.accent); // brand cue
visuals.widgets.hovered.fg_stroke    = Stroke::new(1.0, pal.hover_text);

visuals.widgets.active.weak_bg_fill  = pal.accent_hover;
visuals.widgets.active.bg_fill       = pal.accent_hover;
visuals.widgets.active.fg_stroke     = Stroke::new(1.0, pal.on_accent); // ≥4.4:1
```

The pressed (active) state keeps the brand accent fill + `on_accent` text
(unchanged, measured ≥ 4.4:1). Selected widgets (tabs, checkboxes) are untouched:
`selection.bg_fill = accent` with `selection.stroke = on_accent`.

## Consequences

- Hover feedback is less colorful (gray instead of accent-blue) but always
  readable — the user's explicit requirement ("gray, seen on any theme").
- New `Palette` fields `hover_fill` / `hover_text`; the reference values are
  documented in theme-contract.md (palette table + §7).
- Regression tests:
  - `hover_text_is_gray_and_readable_on_hover_fill_in_every_theme` asserts
    ≥ 4.5:1 contrast for every theme and that `hover_text != on_accent`.
  - `apply_writes_palette_and_spacing_to_both_egui_themes` now also asserts
    `hovered.weak_bg_fill` and the gray `hovered.fg_stroke` reach **both**
    egui theme slots (the ADR-0020 cross-platform surface).
- The diagram tooltip (black-alpha background, white text) is unchanged — it is
  a custom painter, not an egui widget state, and stays legible in all themes.
