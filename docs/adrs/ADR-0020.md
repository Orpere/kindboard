# ADR-0020 — Cross-platform theme determinism: write the palette to both egui theme styles

- **Status:** Accepted
- **Date:** 2026-09-14

## Context

kindboard's custom visuals (dark / light / high-contrast palettes, ADR-0016) were
applied with `Context::set_visuals(visuals)` and `Context::set_global_style(style)` in
`theme::apply_theme` (`crates/kindboard-app/src/theme.rs`).

User report: **"the colors are not working on Windows and Mac — it only works well on
Fedora 44"**.

### Root cause (verified against vendored egui 0.36.2 / egui-winit 0.36 sources)

In egui 0.36, both `set_visuals` and `set_global_style` mutate **only the currently
active theme style**:

- `Context::set_visuals` = `style_mut_of(self.theme(), |style| style.visuals = visuals)`
- `Options::theme()` resolves `ThemePreference` (default **`System`**) against
  `system_theme`, which `egui-winit` feeds from winit every input pass.

Sequence of failure:

1. `KindboardApp::new` runs `theme::apply(&ctx)` **before the first input pass**, when
   `system_theme` is still `None` → `theme()` falls back to `Dark` → the custom palette
   is written into the **dark style only**; the light style keeps egui's defaults.
2. On **Windows and macOS**, winit reliably reports the OS theme; with the OS in light
   mode (the default on most machines), the first input pass flips the active style to
   **Light** → the UI renders egui's untouched default light visuals — kindboard's
   brand palette disappears ("colors not working").
3. On the **Fedora 44** machine (dark desktop theme, or no theme reported by the
   compositor) the active style stayed `Dark` → the custom palette rendered correctly.

The theme picker (`theme::set_theme`) suffered the same defect: the re-applied palette
only ever landed in the currently-active (system-derived) style.

### Secondary, upstream limitation (macOS only)

On macOS, egui-wgpu 0.36.2 configures the surface with
`SurfaceColorSpace::Auto` (wgpu 30 default → `Srgb` for 8-bit formats). wgpu-hal's Metal
backend maps `Srgb` to `CAMetalLayer.setColorspace(nil)` — an **unmanaged** layer — so on
wide-gamut (Display P3) Macs the sRGB bytes are presented without colour management and
saturated colors are oversaturated. Tracked upstream as
[gfx-rs/wgpu#10013](https://github.com/gfx-rs/wgpu/issues/10013) (open as of 2026-09-14;
no in-API workaround for 8-bit surface formats — eframe exposes no `color_space` knob).
Effect is a subtle saturation shift (largest on saturated mid-tones), not the wholesale
theme loss fixed here. Revisit when wgpu ships the fix and eframe upgrades.

## Decision

`theme::apply_theme` builds the final `Style` (custom `Visuals` **plus** spacing) and
writes that single unit to **both** `egui::Theme::Dark` and `egui::Theme::Light` via
`Context::set_style_of(theme, style)`:

```rust
let mut style: Style = (*ctx.global_style()).clone();
style.visuals = visuals;
// …spacing…
for theme in [egui::Theme::Dark, egui::Theme::Light] {
    ctx.set_style_of(theme, style.clone());
}
```

- `set_style_of` replaces the whole style per theme — no ordering hazard between
  `set_visuals` and `set_global_style` (writing `Style.visuals` directly avoids the
  style-clobbers-visuals ordering bug).
- `theme_preference` stays `System` — the native window theme (titlebar) still follows
  the OS; only the in-app palette is made deterministic.
- Runtime OS-theme flips (macOS/Windows dark-mode toggle while the app is open) switch
  the active style — but both styles now carry the kindboard palette, so rendering
  never regresses to egui defaults.

### Regression tests

- `apply_writes_palette_and_spacing_to_both_egui_themes` — both styles carry the Dark
  palette + spacing after `apply`.
- `set_theme_reapplies_both_egui_themes` — both styles carry the new palette after a
  picker swap (Dark → HighContrast → Light).
- Both tests take `THEME_TEST_LOCK` — the test harness runs tests on parallel threads
  and the `CURRENT` palette index is a process-global `AtomicU8`.

### Adjacent fix

`Settings` deserialization gained `#[serde(default = …)]` on
`remember_last_wizard` / `poll_interval_secs`: a minimal, README-documented
`{"theme":"light"}` settings file previously failed the whole parse (missing fields)
and silently fell back to Dark — `theme_from_settings` only ever saw `None`.
Regression test: `partial_settings_file_loads_with_defaults_for_missing_fields`.

### Verification

- Headless screenshot harness (xvfb, `--screenshot`): corner pixel and dominant-color
  histogram match the palette for each theme — Dark `#12161c`, Light `#f5f7fa`,
  HighContrast `#000000`.
- `scripts/check-targets.sh`: windows-gnu (check + clippy) and both darwin targets
  compile clean.

## Consequences

- UI rendering is identical on Linux, Windows, and macOS regardless of the OS theme,
  at startup and on runtime theme changes.
- The macOS wide-gamut saturation deviation remains until upstream wgpu fixes #10013;
  documented here, no app-side workaround exists.
- `theme.rs` grows two regression tests and a test lock; no public API change.
