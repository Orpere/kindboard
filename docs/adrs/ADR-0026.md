# ADR-0026 — Strong text must carry an explicit theme color (egui 0.36 `strong_text_color` coupling)

- **Status:** Accepted
- **Date:** 2026-09-15
- **Supersedes:** nothing (fixes a regression surfaced after ADR-0025)

## Context

User report: in the Light theme the dependency names (and every other
emphasized label — headers, the app title, cluster card names) render
white on the pale background and cannot be read. Pixel forensics on a
headless Xvfb capture confirmed it: the tool names in the dependencies
panel were painted `(249..255, 249..255, 249..255)` — white letters on
the `0xf5f7fa` background (~1.03:1). On the Dark theme the same text
rendered near-black on the dark background — invisible in both themes.

## Root cause

egui 0.36 derives the color of *strong* text (any `RichText` with
`strong()` and no explicit `.color(...)`) from the **active widget text
color**:

```rust
// egui 0.36.2, RichText::get_text_color:
} else if self.strong {
    Some(visuals.strong_text_color())
}

// Visuals::strong_text_color:
self.widgets.active.text_color()   // = active.fg_stroke.color
```

kindboard's R8 rule deliberately sets `widgets.active.fg_stroke` to
`on_accent` (white on Light, `0x060d12` on Dark) so pressed-button text
stays legible on the accent fill. Before egui 0.36, `strong_text_color()`
was a dedicated dark/light value and the coupling did not exist; after
the egui 0.36 upgrade every bare `.strong()` silently inherited the
R8 `on_accent` color — white-on-light, near-black-on-dark.

The bug was invisible in earlier releases only by accident: most strong
labels sat on filled surfaces. The dependency panel and headers put them
on the raw background, which is where the user hit it.

## Decision

1. **New palette token `strong_text`** — the emphasized-text color per
   theme: `0xe9f1f7` (Dark), `0x1f262e` (Light), `WHITE`
   (HighContrast). Both choices clear ~14:1 on their background.
2. **Strong text is always explicit.** `theme::strong(text)` returns a
   `RichText` carrying `.strong()` **and** `.color(pal().strong_text)`;
   every `ui.strong(...)` / `.strong()` call site that did not already
   have an explicit color was converted to use it. Explicit
   `RichText` colors take precedence over egui's derived strong color,
   so this is deterministic regardless of future egui changes.
3. **R8 is unchanged** — `active.fg_stroke` stays `on_accent`; pressed
   buttons keep their measured ≥ 4.4:1 contrast. The two requirements
   are decoupled at the call sites instead of fighting over one egui
   field.
4. **Locked by a regression test** (`strong_text_contrasts_with_bg_in_
   every_theme`): `strong_text` ≥ 4.5:1 on `bg` in all three themes and
   never equal to `on_accent`.

## Consequences

- All emphasized labels are readable in every theme; verified at pixel
  level on headless captures (Light: `(31,38,46)` cores on `0xf5f7fa`;
  Dark: `(233,241,247)` cores on `0x12161c`).
- Future strong text must go through `theme::strong(...)` or an explicit
  `.color(pal().strong_text)`; a bare `.strong()` reintroduces the bug.
- Docs: `docs/theme-contract.md` palette table gains the `strong_text`
  row; howto screenshots were regenerated with the fixed build.
