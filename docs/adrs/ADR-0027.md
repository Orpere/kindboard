# ADR-0027 — Enterprise compliance hardening & CI adoption

- **Status:** Accepted
- **Date:** 2026-09-15
- **Supersedes:** ADR-0017 (in part — its "no GitHub Actions / Makefile-only
  releases" stance, Context and line 232; the osxcross darwin cross-build
  design remains the local `make release` darwin path)

## Context

kindboard grew to a point where its release and supply-chain posture had to be
defensible without depending on the author's laptop. Prior state (ADR-0017,
P22): *"releases are Makefile-driven; the repo deliberately has no CI
workflows."* That was the right call when the pipeline was one machine and one
operator, but it left three gaps for an enterprise-facing tool:

1. **No reproducible, always-on quality gate.** fmt/clippy/tests could only run
   on a developer's box, on their schedule.
2. **No supply-chain evidence.** Nothing scanned advisories, license terms, or
   secrets; releases carried no signature, no provenance, and no SBOM — a
   consumer could not distinguish a genuine release from a tampered one beyond
   the SHA256SUMS file.
3. **Single-producer release risk.** A release existed only if the author ran
   `make release` on a machine with the right cross toolchains installed.

This ADR adopts GitHub Actions for CI/CD and security, keeps the local
Makefile pipeline as a peer producer, and pins every third-party action to a
commit SHA so the workflows are as supply-chain-clean as the app they build.

## Decision

### 1. Three workflows, each with one job family

| Workflow | Trigger | What it enforces |
|---|---|---|
| `.github/workflows/ci.yml` | push to `main` + every PR | rustfmt check, clippy `-D warnings`, `cargo test --workspace`, shellcheck over `scripts/*.sh`; then a 3-OS release-build matrix (ubuntu / macos-13 / macos-14 / windows) with a `kindboard --version` smoke test (exits before GUI init, safe on headless runners) |
| `.github/workflows/security.yml` | push to `main`, every PR, weekly cron (`17 3 * * 1`) | `cargo audit` (RustSec, `--deny unmaintained --deny unsound --deny yanked`), `cargo deny check` against `deny.toml`, gitleaks over full history, dependency review on PRs |
| `.github/workflows/release.yml` | tag push matching `v*` | builds all four release artifacts, generates `SHA256SUMS`, keyless-signs everything with cosign, attaches SLSA provenance, generates + signs an SPDX SBOM, and publishes the GitHub release |

### 2. SHA-pinned action policy

Every `uses:` in all three workflows (plus dependabot's config) is pinned to a
**40-hex commit SHA** with a `# tag:` comment naming the human-readable
version — 37 pins total. Rationale: tags and branch heads move; a commit SHA
cannot. Renovate/dependabot-style bumps are manual (three pins resolve to
moving branch heads — `dtolnay/rust-toolchain@stable`,
`actions/dependency-review-action@v4`, `rustsec/audit-check@v2` — noted as a
revisit-on-next-touch item), but nothing drifts silently.

### 3. `deny.toml` policy (repo root, enforced by the Security workflow)

- **Licenses:** allowlist of 15 SPDX IDs, verified against the full 503-crate
  lockfile; an unknown license fails the gate until a human reviews it.
- **Bans:** `multiple-versions = "warn"`, `wildcards = "deny"`.
- **Sources:** `unknown-registry = "deny"`, `unknown-git = "deny"`.
- **Advisories:** `unmaintained = "all"`, `unsound = "all"` (stricter than the
  workspace-only default), and `yanked = "deny"` (stricter than the default
  `warn` — a yanked transitive dep fails until the lockfile is bumped).

### 4. Tag-triggered release pipeline (release.yml)

On `git tag vX.Y.Z && git push --tags`, the `release` job (after the four
build jobs) does, in order: download all artifacts → `sha256sum` →
`SHA256SUMS` → install cosign → generate SPDX SBOM (anchore) → **keyless-sign**
every artifact, `SHA256SUMS`, and the SBOM with `cosign sign-blob` (Fulcio
certificate + Rekor transparency log via ambient GitHub OIDC, no long-lived
key material) → **attest build provenance** with
`actions/attest-build-provenance` (SLSA) → publish the GitHub release with
release notes generated from the tag's history.

### 5. Dual-producer release model

Two producers emit the **same artifact contract** (names and layout are the
contract, and they match `scripts/build.sh` → `dist/`):

- **CI (`release.yml`) is the canonical producer for tagged releases.** It
  builds natively on real macOS/Windows runners, so it needs no osxcross or
  mingw — and it is the only producer that emits cosign signatures, SLSA
  attestation, and an SBOM.
- **Local `make release` remains for offline and cross builds** — environments
  with no network to GitHub, or where the deterministic Linux tarball and the
  byte-reproducible Windows zip (CI's `Compress-Archive` zip is *not*
  byte-reproducible due to timestamps) matter. Its darwin path still uses the
  ADR-0017 osxcross design; its windows path still uses mingw (ADR-0019).

The contract (artifact list) is: `kindboard-linux-x86_64.tar.gz` (ubuntu,
deterministic), `kindboard-darwin-x86_64.tar.gz` (macos-13 native),
`kindboard-darwin-arm64.tar.gz` (macos-14 native),
`kindboard-windows-x86_64.zip` (windows native), `SHA256SUMS`, per-file
cosign `.sig` + `.pem`, SLSA provenance, and `kindboard-sbom.spdx.json`.

### 6. Permission scoping (least privilege)

Top-level `permissions: contents: read` on every workflow. The only
escalations are: the release job (`contents: write`, `id-token: write`,
`attestations: write` — the minimum set for signing, attesting, and publishing
a release), and the dependency-review job (`pull-requests: read`). No job
holds `actions: write`, `checks: write`, or org-level scopes.

## Consequences

- **Pros.** Every PR is gated by fmt/clippy/tests/shellcheck + audit/deny/
  gitleaks/dependency-review before merge; releases are signed, attested, and
  SBOM'd, so consumers can verify provenance out-of-band (cosign) and
  maintainers get a reproducible tag-triggered release without needing local
  cross toolchains.
- **Costs.** Third-party GitHub Actions are now part of the trust surface —
  mitigated by SHA-pinning and by keeping the entire pipeline reproducible
  locally via `make release`. CI macOS/Windows runners add hosted-runner
  minutes. The Windows zip from CI is not byte-reproducible; integrity there
  comes from SHA256SUMS + cosign + provenance (deterministic zips stay a
  local-build feature).
- **Still out of scope.** Platform code signing (Apple Developer ID +
  notarization, Windows Authenticode) — CI artifacts remain cosign-signed but
  not platform-signed; see `docs/macos-distribution.md` and the threat model.
- **Docs touched.** `docs/threat-model.md` (T4–T6, T9), `SECURITY.md`,
  `CONTRIBUTING.md`, `README.md` (CI badge, Security section), `Makefile`
  header, and `docs/architecture.md` (§3.3 CI/CD system).
