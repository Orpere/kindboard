# ADR-0017 — Darwin release builds via osxcross (local, Makefile-driven)

- **Status:** Accepted
- **Date:** 2026-09-14

## Context

kindboard ships only `dist/kindboard-linux-x86_64.tar.gz` today; no darwin
artifact has ever been released. `scripts/build.sh` hard-skips darwin targets on
non-Darwin hosts (`SKIPPED: run this script on macOS`), so `make build-all`
cannot produce macOS binaries from this Linux box. The app itself is
macOS-ready — `OsKind::Macos`, `darwin-amd64`/`darwin-arm64` dependency digests,
and brew-cask/formula install plans all exist and are tested (P23 intake) — the
gap is purely in the **release artifact pipeline**.

User requirement (P23): *"make sure it can be compiled on the latest mac or
compile it and tag the release with linux and mac."* Mechanism chosen by the
user: **osxcross cross-compilation on this Linux box** (Fedora 44, x86_64 host,
rustc/cargo 1.98.1, rustup present, passwordless sudo dnf, 16 cores, 707G disk).
No GitHub Actions (P22: releases are Makefile-driven; the repo deliberately has
no CI workflows — this design preserves that).

Targets: `aarch64-apple-darwin` + `x86_64-apple-darwin`. Rust std for both is
prebuilt (`rustup target add`; `static.rust-lang.org` reachable). Binaries
cannot be executed here (no Mac hardware, no macOS VM) — QA is limited to the
full host-side test suite, `cargo clippy` for darwin targets, Mach-O structural
inspection, and an ad-hoc code-signature check.

The dependency graph that must cross-link is the #1 risk: `eframe 0.36`
(winit 0.30.13, wgpu 30, accesskit 0.24, egui-wgpu) + `rfd 0.17` reach Apple
frameworks via objc2 0.6 runtime dispatch — Metal, CoreGraphics, AppKit,
QuartzCore, CoreText, CoreAudio must resolve from the SDK. `kindboard-core`
additionally pulls `ring 0.17.14` (via kube→rustls 0.23), which compiles C/asm
at build time through the `cc` crate and therefore needs a *target* C compiler
and archiver, not just a linker.

## Decision

### 1. SDK selection — mirror, version, digest pin, deployment target

- **Mirror:** `github.com/joseluisq/macosx-sdks` (osxcross-packaged SDKs, each
  release carries a `sha256sum` published in `macosx_sdks.json`; actively
  maintained through macOS 26). `phracker/MacOSX-SDKs` is **rejected** — it
  caps at macOS 11.3 (Big Sur) and does not satisfy "latest macOS".
- **SDK:** `MacOSX26.1.sdk.tar.xz` (macOS **Tahoe**, darwin 25.1.0, released
  2025-11-03) — the newest SDK on a maintained, digest-verifiable mirror, i.e.
  literally the latest macOS SDK. Pinned **digest**:
  `beee7212d265a6d2867d0236cc069314b38d5fb3486a6515734e76fa210c784c`.
  - Pin **location:** a constant block in `scripts/build.sh` (single source of
    truth for the release pipeline) — `MACOSX_SDK_VERSION=26.1`,
    `MACOSX_SDK_URL=…/releases/download/26.1/MacOSX26.1.sdk.tar.xz`,
    `MACOSX_SDK_DIGEST=beee7212…`. This ADR is the design record; build.sh is
    the executable pin. No `.cargo/config.toml`, no committed SDK.
  - **Fallback pin:** `MacOSX15.5.sdk.tar.xz` (Sequoia, darwin 24.5.0, digest
    `c15cf0f3f17d714d1aa5a642da8e118db53d79429eb015771ba816aa7c6c1cbd`) if 26.1
    proves incompatible with the installed osxcross/clang.
- **Deployment target** (`MACOSX_DEPLOYMENT_TARGET`): **`10.13` for
  x86_64-apple-darwin**, **`11.0` for aarch64-apple-darwin**.
  - Rationale: the deployment target is a *floor*, not a ceiling — a binary
    built against SDK 26.1 with target 10.13 still runs on the latest macOS.
    `10.13` is above Rust's x86_64 floor (10.12) and winit's floor (10.11,
    "regularly tested on 10.14"), and below nothing eframe 0.36/objc2 0.6
    require; it keeps Intel Macs from 2017+ working. `11.0` for arm64 is the
    hardware floor (no arm64 Mac predates Big Sur) and Rust's baked default.
  - These are per-arch, set inside build.sh's per-target loop (see §3), not a
    single global export.

### 2. Toolchain layout — where osxcross lives and how it is detected

- **Source:** `git clone https://github.com/tpoechtrager/osxcross
  ~/.local/src/osxcross`.
- **Install prefix:** `TARGET_DIR=$HOME/.local/opt/osxcross` →
  `~/.local/opt/osxcross/bin/{x86_64,aarch64}-apple-darwin*-clang`,
  `...-ar`, plus `osxcross-conf`, `xcrun`.
- **Build flavor:** **`latest`** (cctools 1030.6.3 + **ld64 956.6** from
  Xcode 16) as primary — Apple's real ld64 is the most faithful linker for
  Metal/CG/AppKit resolution and **ad-hoc signs arm64 automatically**. **`llvm`**
  (ld64.lld) is the documented fallback if `latest` fails to build on Fedora 44
  (osxcross calls it "easiest to build"); lld also ad-hoc signs arm64, but the
  arm64 signature is then verified by §6 regardless of flavor. Build-time
  `OSX_VERSION_MIN=10.13` so the wrapper's *default* min is sane even for the
  ring C compile (rustc overrides it per-target via `MACOSX_DEPLOYMENT_TARGET`).
- **Detection in build.sh:** env var **`OSXCROSS_DIR`** (default
  `$HOME/.local/opt/osxcross`; overridable via `KINDBOARD_OSXCROSS_DIR` or a
  pre-set `OSXCROSS_DIR`) marks the install root. The verified SDK tarball is
  cached in **`~/.local/share/kindboard/sdk/`** (overridable via
  `KINDBOARD_MACOSX_SDK_CACHE_DIR`) — build-time convenience only; the built
  toolchain already embeds the SDK. A darwin
  target is buildable when `$OSXCROSS_DIR/bin/x86_64-apple-darwin*-clang` **and**
  `$OSXCROSS_DIR/bin/aarch64-apple-darwin*-clang` exist (globbing tolerates the
  version suffix in the wrapper name). **When absent:** keep the existing
  graceful `SKIPPED` behavior, upgraded to name the missing piece and the one
  command to fix it (`osxcross not found at $OSXCROSS_DIR — see
  docs/adrs/ADR-0017.md`). Plain-Linux and native-macOS developers are
  unaffected (macOS hosts build darwin natively; Linux hosts without osxcross
  skip with guidance).

All of the above is automated: `make darwin-bootstrap`
(scripts/bootstrap-darwin.sh) verifies and installs host packages (sudo,
confirm-first or `KINDBOARD_BOOTSTRAP_YES=1`), rustup targets, rcodesign, and
the osxcross toolchain + digest-pinned SDK. `make dist-macos` /
`make build-all` / `make release` call it automatically; the script is
idempotent.

### 3. Env-var strategy — no committed `.cargo/config.toml`

A committed `.cargo/config.toml` pointing `*-apple-darwin` linkers at an
absolute osxcross path would break every normal dev build and every native
macOS build. Instead, **build.sh sets everything inside the per-target loop**
(where `os`, `arch`, and `target` are already computed):

| Env var (set per darwin target) | Value |
|---|---|
| `CARGO_TARGET_<TRIPLE>_LINKER` | `$OSXCROSS_DIR/bin/<arch>-apple-darwin*-clang` |
| `CC_<arch>_apple_darwin` | same clang wrapper (ring 0.17.14 C compile) |
| `AR_<arch>_apple_darwin` | `$OSXCROSS_DIR/bin/<arch>-apple-darwin*-ar` (ring) |
| `MACOSX_DEPLOYMENT_TARGET` | `10.13` (x86_64) / `11.0` (aarch64) |
| `CFLAGS_<arch>_apple_darwin` | `-O2`. The min-version is enforced through `MACOSX_DEPLOYMENT_TARGET` (the clang wrapper applies it to ring's C objects too) — verified in the Mach-O headers (`LC_BUILD_VERSION` / `LC_VERSION_MIN_MACOSX`) |

Notes: `<TRIPLE>` is the rustup triple upper-cased with `-`→`_` (matching
Cargo's convention); `<arch>_apple_darwin` is the `cc`-crate convention
(`aarch64-apple-darwin` → `CC_aarch64_apple_darwin`). These are process-local
exports in one shell iteration — no global mutation, nothing committed, and
native-macOS/normal-Linux builds never see them.

### 4. Artifact layout + naming

- Raw binaries: `dist/aarch64-apple-darwin/kindboard` and
  `dist/x86_64-apple-darwin/kindboard` (unchanged `dist/<target>/` convention).
- Tarballs: **`kindboard-darwin-arm64.tar.gz`** and
  **`kindboard-darwin-x86_64.tar.gz`** — confirmed as proposed. This keeps the
  `kindboard-<os>-<arch>` pattern while using macOS's `arm64` convention instead
  of the rustup-triple's `aarch64`. build.sh's `arch="${target%%-*}"` yields
  `aarch64`, so a **darwin-only display mapping `aarch64 → arm64`** is added for
  the tarball name (the raw-binary directory keeps the rustup triple).
  - Alternative rejected: mechanical `kindboard-darwin-aarch64.tar.gz` — Rust/
    cross-toolchain convention, but "arm64" is what a macOS user searches for.
- **`SHA256SUMS`:** unchanged — build.sh already globs `kindboard-*.tar.gz`, so
  darwin tarballs are included automatically alongside the linux one.
- **Universal (lipo) binary / `.app` bundle / DMG: NO for this release.**
  Binary-only tarballs are the smallest scope that satisfies "compile it and
  tag the release with linux and mac". lipo would double artifact size for
  marginal benefit (most Macs are arm64 now); `.app`/DMG/notarization are
  impossible here (no Apple credentials on Linux) and add nothing beyond the
  ad-hoc-signed binary (right-click → Open under Gatekeeper). Deferred as a
  later engagement — the design leaves a clean seam (`x86_64-apple-darwin*-lipo`
  already exists in osxcross for a future universal build).

### 5. Makefile surface + `make release` behavior

- New target **`dist-macos`**: `KINDBOARD_REQUIRE_DARWIN=1 ./scripts/build.sh
  aarch64-apple-darwin x86_64-apple-darwin` — darwin is *required*; absent
  osxcross or a failed darwin build exits non-zero.
- **`build-all`** unchanged (`--all`); build.sh's `--all` already includes both
  darwin triples and now *attempts* them when osxcross is detected (best-effort).
- **`make release`** gains a `KINDBOARD_REQUIRE_DARWIN ?= 0` knob:
  - first purges stale darwin artifacts (`rm -f dist/kindboard-darwin-*.tar.gz`
    + the two `dist/*-apple-darwin/` dirs) so SHA256SUMS can never ship a
    previous run's darwin assets,
  - always `$(MAKE) build` (linux host — still the hard gate),
  - then darwin: **required** when `KINDBOARD_REQUIRE_DARWIN=1` — the exported
    knob makes the single `$(MAKE) build` pass produce host + both darwin
    targets (no second `dist-macos` call), and missing darwin assets abort
    before tagging; else **best-effort** (`-$(MAKE) dist-macos` with a loud
    `WARNING: release will lack darwin assets` when no
    `kindboard-darwin-*.tar.gz` exists),
  - then tag `v$(VERSION)` and `gh release create` with
    `find dist -name 'kindboard-*.tar.gz'` + `SHA256SUMS` (unchanged — it ships
    whatever exists).
  - Net contract: on this box the actual v0.1.4 ship runs
    **`KINDBOARD_REQUIRE_DARWIN=1 make release`** (linux+mac mandatory); on any
    other machine `make release` still works and ships linux-only with a warning
    — "no broken release on any machine" is preserved.

### 6. Risk register (top 5, each with mitigation + escalation)

| # | Risk | Mitigation | Escalation |
|---|---|---|---|
| 1 | **Apple framework link failure** — winit/wgpu/accesskit/rfd → Metal/CoreGraphics/AppKit/QuartzCore/CoreText/CoreAudio must resolve from the SDK (objc2 runtime dispatch). | `latest` flavor (Apple ld64 956.6, most faithful linker) + newest SDK 26.1 (all frameworks present); per-target link smoke test before the full build. | **debugger** for the specific link error; fall back to `llvm` flavor or SDK 15.5 pin. |
| 2 | **ring 0.17.14 C/asm cross-compile fails** (via `cc` crate; needs target C compiler, not just linker). | Set `CC_<arch>_apple_darwin` + `AR_<arch>_apple_darwin` + `CFLAGS_<arch>_apple_darwin` (§3); verify a `ring` build for one darwin target first. | debugger on the `cc`/ring build.rs error; if ring cannot cross-compile, escalate to tech-lead (rustls provider swap is out of scope for this engagement). |
| 3 | **SDK mirror availability / integrity / supply-chain** — community redistribution of Apple's SDK (Xcode SLA terms), mirror could move or drop the release. | Digest pin + `MACOSX_SDK_DIGEST` compare before use; keep a local cached copy of the verified tarball (`~/.local/share/kindboard/sdk/`, see §2); manual fallback pin 15.5 (never auto-switched); download failure is a hard failure under `KINDBOARD_REQUIRE_DARWIN=1` and warn-and-continue otherwise. | Switch pin constant in build.sh; if mirror is down, reuse the cached tarball. License caveat documented here (build-time tool only — never shipped). |
| 4 | **arm64 binary lacks ad-hoc code signature** (no `LC_CODE_SIGNATURE`; ld64 flavor/version dependent). | `latest` ld64 auto-signs arm64; **verify** via `llvm-objdump --macho --private-headers` (§7); post-link fallback with `rcodesign`/`apple-codesign` ad-hoc. | devops applies rcodesign if the check fails; failing that, `llvm` flavor (lld also signs). |
| 5 | **Host regression from installing clang/cmake/llvm** (dnf) — the host linux build must keep working. | Install only what osxcross needs (clang, cmake, lld/llvm-libs, libtapi); never replace the system `cc` (osxcross uses its own wrappers); re-run the full host gates after install. | Revert the dnf install / use the `llvm` flavor against the system clang; host gates (fmt/clippy/test) are the regression guard. |

### 7. QA acceptance criteria (checkable on this Linux box)

1. Toolchain present: `$OSXCROSS_DIR/bin/{x86_64,aarch64}-apple-darwin*-clang`
   exist and build.sh detects them; `OSXCROSS_DIR=/nonexistent ./scripts/build.sh
   --all` prints darwin SKIP guidance and still exits 0 (linux host built).
2. SDK digest verified at install time (`sha256sum -c` == `beee7212…`) and SDK
   unpacked into osxcross's `tarballs/` before `./build.sh`.
3. Host gates green with zero regressions after the clang install:
   `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --
   -D warnings`, `cargo test --workspace`.
4. Darwin type-check: `cargo clippy --target aarch64-apple-darwin --package
   kindboard-app -- -D warnings` and the `x86_64-apple-darwin` equivalent pass
   (exercises the darwin `cfg` paths without executing).
5. Binaries produced and structurally correct: `dist/aarch64-apple-darwin/kindboard`
   and `dist/x86_64-apple-darwin/kindboard` are non-empty and `file` reports
   `Mach-O 64-bit executable arm64` / `Mach-O 64-bit executable x86_64`.
6. arm64 signature: `llvm-objdump --macho --private-headers
   dist/aarch64-apple-darwin/kindboard | grep -q LC_CODE_SIGNATURE` (x86_64
   checked opportunistically; arm64 is the requirement).
7. Tarballs `kindboard-darwin-arm64.tar.gz` + `kindboard-darwin-x86_64.tar.gz`
   exist, contain exactly the binary, and are reproducible (`GZIP=-n`,
   owner/group 0, mtime 0 — same as the existing linux tarball).
8. `dist/SHA256SUMS` includes the linux tarball and both darwin tarballs and
   verifies (`sha256sum -c`).
9. `KINDBOARD_REQUIRE_DARWIN=1 make release` tags v0.1.4 and the GitHub release
   carries linux + both darwin tarballs + SHA256SUMS.

## Alternatives considered (rejected)

- **GitHub Actions macOS runner** — simplest darwin build, but P22 removed
  Actions by design (Makefile-driven releases); the user chose osxcross. Rejected.
- **Build on a real Mac** — needs hardware not available here. Rejected.
- **`phracker/MacOSX-SDKs`** — caps at macOS 11.3; does not meet "latest macOS".
  Rejected.
- **Commit a `.cargo/config.toml`** for darwin linkers — breaks normal dev and
  native-macOS builds. Rejected (§3).
- **Universal lipo binary / `.app` / DMG** — larger scope, no notarization
  possible here; deferred, not dropped (§4).
- **Require darwin for `make release` unconditionally** — breaks releases on
  plain-Linux/macOS machines without osxcross. Rejected in favour of the
  `KINDBOARD_REQUIRE_DARWIN` knob (§5).

## Consequences

- This machine becomes the darwin build host; the release pipeline remains
  100% Makefile-driven with no CI.
- One new host dependency (osxcross + clang/cmake/llvm via dnf) that is
  *not* in the repo; reproducibility is carried by the pinned SDK digest + the
  `OSXCROSS_DIR` convention, not by committing the toolchain.
- `scripts/build.sh` grows: osxcross detection, per-darwin-target env exports
  (§3), the `aarch64→arm64` tarball-name mapping, and a
  `KINDBOARD_REQUIRE_DARWIN` policy. `Makefile` grows `dist-macos` and the
  release knob.
- Binaries are ad-hoc-signed, not notarized: macOS Gatekeeper requires
  right-click → Open on first run. Documented as a known limitation until Apple
  credentials exist (later engagement).
- macOS users on arm64 need macOS 11.0+; Intel users need 10.13+ — both run
  the "latest" macOS fine (floor, not ceiling).

## Verification

- This ADR's acceptance criteria (§7) are the verification contract; devops
  runs them at install/build time and reports each item PASS/FAIL.
- The `LC_CODE_SIGNATURE` + Mach-O checks are the executable-proof stand-in for
  "runs on macOS" given no Mac hardware/VM is available here.
