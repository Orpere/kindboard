# ADR-0019 — Windows support: windows-gnu cross-build, cfg-gated core, user-scope installer

- **Status:** Accepted
- **Date:** 2026-09-14
## Context

kindboard is a Rust egui/eframe desktop app (kindboard-core + kindboard-app).
User requirement: **"get all code to be agnostic and compile to the main
operation systems and run as user no need for permissions"** — add Windows to
the existing Linux + macOS support; the app runs as a plain user, zero
elevation, zero permission prompts.

Audited Unix surface (line refs against current HEAD):

- `exec.rs` — process groups via `nix`: `#[cfg(unix)] process_group(0)`
  (188-189), cancel-watcher TERM/KILL ladder (212-224),
  `terminate_group`/`kill_group` (362-369), `signal_group` killpg
  (537-541), Drop guard (510-522), nix test poll (987-991).
- `fsutil.rs` (58-68, 178-181) and `kubeconfig.rs` (303-320: `split_paths`
  is `;`-aware, `dirs::home_dir()` → `%USERPROFILE%`) — already portable.
  **Both: no change needed.**
- `deps/mod.rs` — `OsKind` lacks Windows (261-268); `PkgManager` lacks
  winget/choco (271-281); `detect_platform` (296-318); `find_in_path`/
  `is_executable` (330-352) wrong on Windows (no PATHEXT — `kind.exe`
  is never `kind`); `local_bin_dir` (354-360) portable (dirs crate);
  pkg-match (579-642); `render_platform`/`platform_key` map non-macos →
  `"linux"` (675-690, 700-708); `build_binary_steps` (710-838) hard-codes
  Unix coreutils; test helper (1036-1043).
- `main.rs` — `--detach` unix-only (283-312, 404-408); no
  `windows_subsystem` attribute (release exe would pop a console).
- `worker.rs`/`state/`/`k8s/` — no Unix code; docker is reached only via
  the `docker` CLI subprocess (worker.rs:192 → `docker info`), never the
  socket (zero references to `/var/run/docker.sock` or `DOCKER_HOST`).
- `scripts/build.sh` — SKIPs windows targets (357-360); `SHA256SUMS`
  covers zips (606); `make release` already uploads `kindboard-*.zip`;
  `scripts/install-macos.sh` is the user-scope installer template.

Empirical gate (this box, Fedora 44, `mingw64-gcc-16.1.1-1.fc44`
installed): `cargo check --target x86_64-pc-windows-gnu` fails **only**
on the 7 `nix` references (nix 0.31.3 has no Windows support); after
cfg-gating nix in a scratch copy, the whole workspace (eframe 0.36.2,
wgpu 30.0.1, winit, ring 0.17.14, kube/rustls) compiles; `--all-targets`
adds 2 test spots (exec.rs 987-991, deps/mod.rs 1036-1043).

## Decision

**Toolchain.** Cross-build `x86_64-pc-windows-gnu` via `dnf install
mingw64-gcc` (already installed): plain GCC + rustup std, empirically
compiling end-to-end (ring supports windows-gnu). Native Windows stays
the rustup default (`stable-msvc`); the installer ships prebuilt
binaries and source build is a documented one-liner.

**cfg-gating map** (exact edits in the checklists): exec.rs — nix calls
become `#[cfg(unix)]`; Windows tree-kill is the bundled
`taskkill /PID <n> /T [/F]` (fire-and-forget `std::process::Command`);
`spawn()` gains `#[cfg(windows)] creation_flags(CREATE_NO_WINDOW)`
(tokio 1.52.3 exposes it — no console flashes when the GUI spawns CLI
tools). deps/mod.rs — `OsKind::Windows`, `PkgManager::{Winget,Choco}`,
PATHEXT-aware `find_in_path`, winget/choco arms, a Windows branch of
`build_binary_steps` using bundled `curl.exe`/`tar.exe` (Win10 1803+) +
PowerShell one-liners for mkdir/mv/rm, no chmod. main.rs —
`windows_subsystem = "windows"` + a `cfg(windows)` detach twin via
`CREATE_NO_WINDOW`. kubeconfig.rs, fsutil.rs, worker.rs: zero changes.

**Deps installer on Windows.** winget → choco → binary fallback into
`%USERPROFILE%\.local\bin`. Registry gains winget/choco IDs and
`windows-amd64` sha256 pins (transcribed from upstream at implementation
time, same discipline as the existing matrix); kubectx/kubens are shell
scripts — explicitly unsupported with an honest error.

**Zero elevation.** Verified: no sudo/runas anywhere in the app or
installers; kindboard never elevates. Honest boundary: winget/choco may
raise UAC *themselves* when they install machine-scope software (Docker
Desktop) — that is the package manager's elevation, not kindboard's;
documented as such.

**Installer.** `scripts/install-windows.ps1` mirrors install-macos.sh:
resolve version, download `kindboard-windows-x86_64.zip` + SHA256SUMS,
`Get-FileHash` verify, `Expand-Archive` to `%USERPROFILE%\.local\bin`,
`Remove-Item -Stream Zone.Identifier` (kills Mark-of-the-Web →
no SmartScreen prompt), idempotent `--version` check, PATH hint printed
(never mutated). No `RunAs`, no `#Requires -RunAsAdministrator`.

**build.sh.** Add `x86_64-pc-windows-gnu` to `SUPPORTED_TARGETS`
(118-123); replace the windows SKIP (357-360) with mingw detection →
`CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER=x86_64-w64-mingw32-gcc`;
missing toolchain → SKIP with `dnf install mingw64-gcc` guidance, or
ERROR under new knob `KINDBOARD_REQUIRE_WINDOWS=1` (mirrors
`KINDBOARD_REQUIRE_DARWIN`). Artifact: `kindboard.exe` copied per-os
(441-442), shipped as deterministic zip `kindboard-windows-x86_64.zip`
(reuse the python3-zipfile helper; member `kindboard.exe`); no tarball
for Windows.

**Verification gate.** New `scripts/check-targets.sh` + `make
check-targets`: `cargo check --workspace --all-targets` for the host and
every available cross target (windows when mingw+std present, darwin when
osxcross ready) + `cargo clippy --workspace --all-targets --target
x86_64-pc-windows-gnu -D warnings`. Tests run on Linux only — no Windows
runner exists; Windows runtime behavior is deferred to user machines
(stated honestly).

## Alternatives considered (rejected)

- **cargo-xwin / msvc cross from Linux** — xwin network-fetches MS CRT +
  SDK headers and layers msvc import-lib complexity; windows-gnu needs
  one dnf package already present and is empirically verified here.
- **arm64 Windows** — no toolchain on this box, thinner ring coverage;
  amd64 only, stated in docs.
- **dirs-crate-free path logic** — `dirs` is already a dependency and
  resolves `%USERPROFILE%` for free.
- **MSI/NSIS installer** — machine-scope installers contradict "run as
  user, no permissions"; the PowerShell script matches install-macos.sh.
- **Write PATH via registry/setx** — 1024-char truncation risk, silent
  account mutation; install-macos.sh doesn't either.
- **Keep `--detach` unix-only** — a trivial Windows twin keeps parity.

## Consequences

- Windows runtime testing deferred to user machines (no Windows runner);
  the compile gate runs on every `make check-targets` / release.
- kind on Windows runs against Docker Desktop (Linux containers) — the
  only UAC the user may see belongs to Microsoft's/Winget's installer,
  never kindboard.
- kubectx/kubens unavailable on Windows — explicit deps-view message.
- Binaries are unsigned (no code-signing certificate): SmartScreen
  prompts are neutralized by Zone.Identifier removal at install time;
  users bypassing the installer script may still see SmartScreen
  heuristics — documented.
- build.sh + check-targets gain one knob and one target; releases gain
  `kindboard-windows-x86_64.zip`.

## Verification

- `cargo check -p kindboard-app --target x86_64-pc-windows-gnu` passes
  (scratch copy in /tmp/opencode/wincheck, shared CARGO_TARGET_DIR, repo
  untouched): the only pre-existing failure was the 7 nix errors; after
  gating, 0 errors. `--all-targets` adds 2 test spots (exec.rs 987-991,
  deps/mod.rs 1036-1043) — both fixed by the plan.
- Post-implementation: `make check-targets` green; `scripts/build.sh
  x86_64-pc-windows-gnu` produces `dist/kindboard-windows-x86_64.zip` +
  SHA256SUMS entry; install-windows.ps1 syntax-checked (pwsh locally if
  available, else on a user machine — stated).
